<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| developer machine → GHCR | The locally-built image and a write:packages PAT cross to GitHub's registry |
| GHCR → Linux VPS | The pulled image and the developer's SSH session cross onto the server |
| server `.env` → container runtime | Production secrets injected at runtime via `env_file`; must stay on the server only |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-05 | Information Disclosure | GHCR PAT (write:packages) | mitigate | Runbook scopes the PAT to `write:packages` only and states it lives on the local machine, used via `docker login`, never committed (D-06) |
| T-03-06 | Information Disclosure | server `.env` (production secrets) | mitigate | Runbook creates `.env` directly on the server from the placeholder template and states it is never committed; `env_file` injects at runtime (DEP-03) |
| T-03-07 | Spoofing / Tampering | image provenance (server pulls from GHCR) | accept | Single-developer, private repo; server pulls a tag the developer pushed. Image signing/digest pinning deferred (out of v1 scope); revisit when CI publishes images (Phase 4) |
| T-03-08 | Denial of Service | duplicate pollers (409 getUpdates) | mitigate | Runbook instructs using a distinct production bot token vs. any local dev token; REL-03 (Phase 2) already enforces single-poller behavior at the app layer |
| T-03-SC | Tampering | package installs | accept | This plan installs no packages; it only documents deploy of the Plan 01 image. No supply-chain surface added. |
</threat_model>
