<task type="checkpoint:decision" gate="blocking">
  <name>Task 1: Decide and apply the durable GHCR pull credential for the server</name>
  <files>(no repo files — GitHub Packages visibility and/or server-side ~/.docker/config.json)</files>
  <read_first>
    - .planning/phases/04-ci-cd-auto-deploy/04-RESEARCH.md (Pitfall 3 + Open Question 1: the job GITHUB_TOKEN is revoked at job end; the server needs a durable pull path — make the package public OR one-time server `docker login` with a read-only fine-grained token)
    - .planning/phases/03-containerize-run-24-7/03-02-SUMMARY.md (the existing manual server runbook: server dir, server-side `docker login`, compose pull/run that the automated deploy now replaces)
    - .github/workflows/ci-cd.yml (the deploy job no longer logs in on the server in-script — so a durable credential must exist independently)
  </read_first>
  <decision>How will the VPS authenticate to GHCR for the recurring automated pulls now that the in-script GITHUB_TOKEN login is removed?</decision>
  <context>
    The Plan 02 deploy script deliberately dropped `echo $GITHUB_TOKEN | docker login` because the job
    token is revoked when the job ends — so it cannot serve `--pull always` on later deploys or after a
    reboot. The server needs a credential that persists. RESEARCH recommends the public-package path as the
    simplest (zero secrets to manage on the server).
  </context>
  <options>
    <option id="public-package">
      <name>Make the GHCR package public</name>
      <pros>Zero server-side credentials; `docker compose up -d --pull always` just works; nothing to rotate or leak; simplest for a solo project</pros>
      <cons>The image (not the secrets — secrets live only in the server .env) is publicly pullable; acceptable since the image contains no secrets by Phase 3 design</cons>
    </option>
    <option id="readonly-login">
      <name>Keep the package private; one-time server `docker login` with a read-only fine-grained PAT</name>
      <pros>Image stays private; least-privilege read:packages token persisted in ~/.docker/config.json survives across deploys/reboots</pros>
      <cons>A long-lived credential to create, store on the server, and eventually rotate; one more manual step</cons>
    </option>
  </options>
  <action>
    Present both options. The recommended path is `public-package` (RESEARCH Open Question 1). After the
    user selects: if `public-package`, the user sets the package visibility to Public in GitHub Packages →
    package settings (the bot is then pullable with no server credential). If `readonly-login`, the user
    creates a fine-grained PAT scoped to `read:packages` and runs `docker login ghcr.io -u <user>
    --password-stdin` once on the VPS so the credential is persisted in `~/.docker/config.json`. Record the
    chosen path in the SUMMARY so the rationale is captured for future deploys.
  </action>
  <verify>
    <human-check>User confirms the GHCR pull path is in place: either the package shows Public in GitHub Packages settings, OR `docker pull ghcr.io/<owner>/telegram_bot_ai/bot:latest` succeeds from a fresh SSH session on the VPS (proving the persisted read-only login works).</human-check>
  </verify>
  <done>The chosen GHCR pull path (public-package or readonly-login) is applied and confirmed pullable from the server, and the decision is recorded in the SUMMARY.</done>
  <resume-signal>Select: public-package or readonly-login (and confirm it has been applied)</resume-signal>
</task>

  </read_first>
  <what-built>
    A single `ci-cd.yml` workflow with a `ci-checks` job (ruff, ruff format, mypy, pytest, docker build) and
    a `deploy` job gated by `needs: [ci-checks]` + `if: github.ref == 'refs/heads/main'`. The deploy builds
    and pushes `ghcr.io/<owner>/telegram_bot_ai/bot:latest`, then SSHes to the VPS and runs
    `docker compose up -d --pull always --force-recreate` followed by `docker image prune -f`. New handler
    tests (Plan 01) and pinned dev tooling are in place; the GHCR pull credential was settled in Task 1.
  </what-built>
  <action>
    Drive a real end-to-end pipeline run and human-verify the three live success criteria (SC-3/SC-4/SC-5)
    that CI cannot self-assert. First run the prerequisite checks (secrets + server `cd` path). Then prove
    the gate NEGATIVELY (deploy is skipped on a PR/non-main run) and POSITIVELY (deploy runs only after a
    green ci-checks on a push to main). Then confirm on the VPS that the server is running the newly built
    image and that no 409 appears in the logs. Follow the numbered steps in <how-to-verify>. If the deploy
    `cd ~/telegram-ai-bot` target does not match the real server dir, correct the `cd` line in `ci-cd.yml`
    (this is the one expected in-flight fix) and re-run.
  </action>
  <how-to-verify>
    Prerequisite check (do first):
    1. In GitHub → repo → Settings → Secrets and variables → Actions, confirm `SERVER_HOST`,
       `SERVER_USER`, and `SERVER_SSH_KEY` all exist.
    2. SSH to the VPS and confirm the deploy `cd` target matches reality: the script uses
       `cd ~/telegram-ai-bot`. Run `ls ~/telegram-ai-bot/compose.yaml ~/telegram-ai-bot/.env`. If the
       directory is different (Phase 3 runbook used `~/telegram-ai-bot`), note the correct path — the
       deploy `cd` line in `ci-cd.yml` must be corrected to match before this run can succeed.

    Negative gate (deploy must NOT run off main):
    3. Open a trivial pull request (or push a throwaway branch). In the Actions tab, confirm the run executes
       `ci-checks` but the `deploy` job is SKIPPED (greyed out / "Skipped"). This proves the `if: ref==main`
       guard. Close the PR.

    Positive end-to-end (SC-3 + SC-4 + SC-5):
    4. Push a small change to `main` (e.g. a README touch). In the Actions tab, open the run: confirm
       `ci-checks` runs and goes green FIRST, and only then does `deploy` start (the run graph shows deploy
       downstream of ci-checks). If you want to also prove the gate blocks bad code, optionally push a commit
       that fails a check on a branch and confirm deploy never starts — optional.
    5. After the run is green, SSH to the VPS and run `docker compose ps` (in the server dir): the `bot`
       service is `Up`, and its image/created time corresponds to this deploy (use
       `docker inspect --format '{{.Created}} {{.Config.Image}}' $(docker compose ps -q bot)` and compare to
       the run timestamp). This confirms the server is running the NEWLY built version (SC-4) — i.e.
       `--force-recreate` actually replaced the container, not the #9259 stale-`:latest` case.
    6. Confirm the bot still replies in Telegram (send it a message) — the new version is live and healthy.
    7. Inspect the deploy-time logs for a 409: run `docker compose logs bot --since 10m | grep -i "terminated by other getUpdates"` (or 409/Conflict). Expect NO matches — the stop-old-then-start-new recreate kept a single poller (SC-5).
  </how-to-verify>
  <verify>
    <human-check>User confirms: the PR/branch run SKIPPED deploy; the push-to-main run ran deploy only after a green ci-checks; `docker compose ps` on the VPS shows the bot Up on the freshly built image; the bot replies in Telegram; and `docker compose logs bot` shows no 409 around the release.</human-check>
  </verify>
  <done>An end-to-end pipeline run is verified: CI-gated deploy (SC-3), server on new version (SC-4), and no 409 during release (SC-5), with any server-path correction applied to ci-cd.yml.</done>
